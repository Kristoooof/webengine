## A probléma: fák Rustban

Egy DOM-csomópontnak van **szülője** és vannak **gyerekei**. C#-ban ez triviális:

```csharp
class Node {
    public Node Parent;
    public List<Node> Children = new();
}
```

Rustban próbáld meg ugyanezt referenciákkal:

```text Nem fordul le
struct Node<'a> {
    parent: Option<&'a Node<'a>>,
    children: Vec<Node<'a>>,
}
```

Ez nem működik. A gyerek a szülőre mutat, a szülő birtokolja a gyereket, és a borrow checker nem engedi, hogy egy érték egyszerre legyen birtokolva és kölcsönadva, miközben módosítod. (A JavaScript például bármikor átrendezheti a DOM-ot!) Három szokásos megoldás létezik:

| Megoldás | Hogyan | Ára |
|---|---|---|
| `Rc<RefCell<Node>>` + `Weak` | Referenciaszámlálás, futásidejű kölcsönzés-ellenőrzés | Bőbeszédű (`.borrow_mut()` mindenhol), lassabb, és futásidőben pánikolhat |
| `unsafe` nyers mutatók | Mint C++-ban | Elveszted a Rust biztonsági garanciáit |
| **Aréna + azonosítók** | Minden csomópont egy `Vec`-ben, a kapcsolatok **indexek** | Egyszerű, gyors, biztonságos ✅ |

## Az aréna

Az ötlet: minden csomópont egyetlen nagy `Vec<Node>`-ban él. Ez az **aréna**. A csomópontok nem referenciákkal, hanem **indexekkel** hivatkoznak egymásra:

```text Ábra
nodes: Vec<Node>
┌───────────────────┬───────────────────┬───────────────────┬────────────────────┐
│ 0: Document       │ 1: <html>         │ 2: <p>            │ 3: "Szia"          │
│ parent: None      │ parent: Some(0)   │ parent: Some(1)   │ parent: Some(2)    │
│ children: [1]     │ children: [2]     │ children: [3]     │ children: []       │
└───────────────────┴───────────────────┴───────────────────┴────────────────────┘
```

Egy index csak egy szám, `Copy`. Annyit tárolhatsz és adhatsz át belőle, amennyit akarsz, a borrow checker nem szól érte. Amikor módosítani kell, a `Document`-en keresztül teszed (`doc.append(parent, child)`), ami az egész arénát `&mut`-ként kezeli.

:::compare Ezt már láttad
@@ Érettségi
Ha emelt infón egy fát vagy gráfot tömbben tároltál, ahol minden elem a szülője **indexét** tárolta (pl. `szulo[i]`), az pontosan egy aréna! A Rozsda DOM-ja ugyanez, csak struktúrával és típusokkal.
@@ C++
A játékmotorok (és az ECS-rendszerek) is így dolgoznak: az objektumok egy nagy tömbben vannak, a hivatkozások pedig „handle”-ök (indexek). Cache-barát (a csomópontok egymás mellett vannak a memóriában), és nincs lógó mutató.
@@ Rust
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct NodeId(pub usize);
```
Egy **newtype**: egy `usize`, saját típusba csomagolva. Így a fordító nem engedi, hogy véletlenül egy sima számot (pl. egy tömbindexet) adj át csomópont-azonosító helyett. Futásidőben semmibe nem kerül.
:::

:::note Mi történik a törléssel?
Ha a JavaScript kitöröl egy elemet a DOM-ból, a csomópontja az arénában marad, csak senki nem hivatkozik rá. Ez egyszerűsített memóriakezelés: az aréna a dokumentummal együtt szabadul fel. A böngészők ennél okosabbak (a 12. modulban szemétgyűjtőt írsz), de egy oldal élettartama alatt ez ritkán számít.
:::

## A típusok

```rust
#[derive(Debug, Clone, PartialEq)]
pub struct ElementData {
    pub name: String,
    pub attrs: Vec<(String, String)>,
}

#[derive(Debug, Clone, PartialEq)]
pub enum NodeData {
    Document,
    Doctype(String),
    Element(ElementData),
    Text(String),
    Comment(String),
}

#[derive(Debug, Clone, PartialEq)]
pub struct Node {
    pub parent: Option<NodeId>,
    pub children: Vec<NodeId>,
    pub data: NodeData,
}

#[derive(Debug, Clone, PartialEq)]
pub struct Document {
    nodes: Vec<Node>,
}
```

A `nodes` mező szándékosan **privát**. Kívülről csak a `Document` metódusain keresztül lehet módosítani, így a `parent` és a `children` mindig összhangban marad.

:::note Miért nem öröklés?
A böngészők C++-ban a DOM-ot hosszú öröklési láncokkal írják (`Node → Element → HTMLElement → HTMLParagraphElement`). Rustban egy `enum NodeData` ugyanezt adja öröklés nélkül, és a `match` garantálja, hogy minden csomópontfajtát kezelj. Ezt ígértük még a 01-06-ban.
:::

mod tests {

    fn sample() -> (Document, NodeId, NodeId) {

        assert_eq!(doc.children(doc.root()), &[html]);
        assert_eq!(doc.parent(p), Some(html));
        assert_eq!(doc.tag_name(p), Some("p"));

        assert_eq!(doc2.text_content(html), "Szia, Rozsda!");
        let _ = doc;
    }

```rust
//! A DOM: a dokumentum fája, arénában tárolva.

/// Egy csomópont azonosítója: index a `Document` arénájában.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct NodeId(pub usize);

impl ElementData {
    pub fn attr(&self, name: &str) -> Option<&str> {
        self.attrs.iter().find(|(n, _)| n == name).map(|(_, v)| v.as_str())
    }

    pub fn id(&self) -> Option<&str> {
        self.attr("id")
    }

    pub fn classes(&self) -> Vec<&str> {
        self.attr("class").map(|c| c.split_whitespace().collect()).unwrap_or_default()
    }
}

impl Default for Document {
    fn default() -> Self {
        Self::new()
    }
}

impl Document {
    pub fn new() -> Document {
        Document { nodes: vec![Node { parent: None, children: Vec::new(), data: NodeData::Document }] }
    }

    pub fn root(&self) -> NodeId {
        NodeId(0)
    }

    pub fn len(&self) -> usize {
        self.nodes.len()
    }

    pub fn is_empty(&self) -> bool {
        self.nodes.len() == 1
    }

    pub fn node(&self, id: NodeId) -> &Node {
        &self.nodes[id.0]
    }

    pub fn create(&mut self, data: NodeData) -> NodeId {
        self.nodes.push(Node { parent: None, children: Vec::new(), data });
        NodeId(self.nodes.len() - 1)
    }

    pub fn create_element(&mut self, name: &str, attrs: Vec<(String, String)>) -> NodeId {
        self.create(NodeData::Element(ElementData { name: name.to_string(), attrs }))
    }

    pub fn append(&mut self, parent: NodeId, child: NodeId) {
        self.nodes[child.0].parent = Some(parent);
        self.nodes[parent.0].children.push(child);
    }

    /// Szöveg hozzáfűzése: ha az utolsó gyerek már szöveg, ahhoz írjuk hozzá.
    pub fn append_text(&mut self, parent: NodeId, text: &str) {
        if let Some(&last) = self.nodes[parent.0].children.last()
            && let NodeData::Text(t) = &mut self.nodes[last.0].data
        {
            t.push_str(text);
            return;
        }
        let id = self.create(NodeData::Text(text.to_string()));
        self.append(parent, id);
    }

    pub fn children(&self, id: NodeId) -> &[NodeId] {
        &self.nodes[id.0].children
    }

    pub fn parent(&self, id: NodeId) -> Option<NodeId> {
        self.nodes[id.0].parent
    }

    pub fn element(&self, id: NodeId) -> Option<&ElementData> {
        match &self.nodes[id.0].data {
            NodeData::Element(e) => Some(e),
            _ => None,
        }
    }

    pub fn tag_name(&self, id: NodeId) -> Option<&str> {
        self.element(id).map(|e| e.name.as_str())
    }

    /// Az összes leszármazott, dokumentum-sorrendben (preorder), önmaga nélkül.
    pub fn descendants(&self, id: NodeId) -> Vec<NodeId> {
        let mut out = Vec::new();
        let mut stack: Vec<NodeId> = self.children(id).iter().rev().copied().collect();
        while let Some(n) = stack.pop() {
            out.push(n);
            stack.extend(self.children(n).iter().rev());
        }
        out
    }

    pub fn find_first(&self, tag: &str) -> Option<NodeId> {
        self.descendants(self.root()).into_iter().find(|&n| self.tag_name(n) == Some(tag))
    }

    pub fn text_content(&self, id: NodeId) -> String {
        let mut out = String::new();
        for n in std::iter::once(id).chain(self.descendants(id)) {
            if let NodeData::Text(t) = &self.nodes[n.0].data {
                out.push_str(t);
            }
        }
        out
    }

    pub fn title(&self) -> Option<String> {
        let t = self.find_first("title")?;
        let text = self.text_content(t);
        Some(text.split_whitespace().collect::<Vec<_>>().join(" "))
    }
}
```
(A `ElementData`, `NodeData`, `Node` és `Document` definíciója a lecke elején van.)

:::why Miért kell az append_text összevonás?
A tokenizer egy szövegtokent ad ki minden szövegdarabra, de egy elemben több darab is egymás után kerülhet. Például a `<p>a</span>b</p>` esetén a kóbor `</span>` miatt két szövegtoken lesz („a” és „b”), és a DOM-ban mégis egyetlen „ab” szöveg-csomópont kell. A szabvány is ezt írja elő („insert a character”: ha az előző csomópont szöveg, ahhoz fűzd). A JavaScriptben a `normalize()` metódus utólag ugyanezt csinálja.

:::card
K: Mi az aréna-minta Rustban?
V: Minden csomópont egyetlen `Vec`-ben él, és egymásra indexekkel (pl. `NodeId(usize)`) hivatkoznak. Így ciklikus kapcsolatok (szülő ↔ gyerek) is biztonságosan tárolhatók.

:::card
