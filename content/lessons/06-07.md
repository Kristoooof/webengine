## Miért pont PNG?

A böngészők tesztjeinek jó része képernyőkép: „ez az oldal pontosan így nézzen ki”. Ehhez egy veszteségmentes képformátum kell. A JPEG elmosná a betűk szélét, a PNG viszont minden pixelt pontosan megőriz. A 05-09-es snapshot tesztek a layout számait rögzítették, a képernyőkép-tesztek a **végeredményt**: ha a raszterizálóban elrontasz valamit, ez veszi észre.

Egy PNG-fájl felépítése:

```text Ábra
89 50 4E 47 0D 0A 1A 0A          aláírás: "\x89PNG\r\n\x1a\n"
┌───────────────────────────┐
│ hossz │ IHDR │ adat │ CRC │    fejléc: szélesség, magasság, színtípus
├───────────────────────────┤
│ hossz │ IDAT │ adat │ CRC │    a pixelek, zlib-tömörítve
├───────────────────────────┤
│ hossz │ IEND │      │ CRC │    vége
└───────────────────────────┘
```

Minden **darab** (chunk) ugyanúgy néz ki: 4 bájt hossz, 4 betűs típus, az adat, és egy 4 bájtos **CRC-32** ellenőrzőösszeg a típusra és az adatra. A számok **big-endian** sorrendben vannak (a legnagyobb helyi értékű bájt elöl), ezt a Rust `u32::to_be_bytes()` csinálja.

Az aláírás bájtjai nem véletlenek. A `\x89` miatt egy szövegszerkesztő nem hiszi szövegnek a fájlt, a `\r\n` és a `\n` pedig elárulja, ha egy rossz FTP-átvitel kicserélte a sorvégeket (03-01).

## A tömörítés, amit kihagyunk

Az IDAT adata egy **zlib**-folyam, ami a **deflate** algoritmussal tömörít. Ennek a megírása egy külön modul lenne (Huffman-kódolás, LZ77). Szerencsére a deflate ismer egy **tárolt** (stored) blokkfajtát is, ami egyáltalán nem tömörít, csak beteszi a bájtokat:

```text Ábra
zlib:     78 01 │ blokk │ blokk │ … │ Adler-32
blokk:    BFINAL │ LEN (2 bájt, LE) │ NLEN = !LEN │ legfeljebb 65 535 bájt adat
```

Egy blokk legfeljebb 65 535 bájtot tárol, ezért egy nagy képet több blokkra kell vágni. Az utolsó blokk első bájtja 1 (BFINAL), a többié 0. Itt a hossz **little-endian** (`to_le_bytes`), mert a deflate így írja. A zlib végén egy másik ellenőrzőösszeg áll, az **Adler-32**, a tömörítetlen adatra.

A pixelek soronként jönnek, minden sor előtt egy **szűrő**-bájttal (filter). A szűrők a tömörítést segítik (pl. „minden pixel a bal szomszédjától való eltérés”). Mi nem tömörítünk, ezért a 0-s szűrőt használjuk: „nincs szűrő”. Egy 960×720-as kép így 2 MB körüli lesz. Egy igazi PNG-író ennek a töredékére tömörítené, de a fájl ugyanúgy szabványos.

## Két ellenőrzőösszeg

**Adler-32**: két összeg 65 521-es (a legnagyobb 2¹⁶ alatti prím) maradékkal. Az `a` a bájtok összege (1-ről indul), a `b` az `a` értékeinek összege. Az eredmény `(b << 16) | a`.

**CRC-32**: egy polinomosztás maradéka. Bitenként számolva: minden bájtot hozzá-XOR-olunk az állapothoz, aztán 8-szor: ha a legalsó bit 1, eltolunk jobbra és XOR-olunk a `0xEDB88320` polinommal, különben csak eltolunk. Az elején és a végén minden bit megfordul (`!crc`).

:::compare Ellenőrzőösszegek
@@ C#
`System.IO.Hashing.Crc32.Hash(adat)` (a .NET 6 óta). A ZIP-fájlok és az Ethernet ugyanezt a CRC-32-t használják.
@@ Python
`zlib.crc32(b"123456789")` és `zlib.adler32(b"Wikipedia")`. Ezekkel ellenőrizheted a sajátodat!
@@ Érettségi
A paritásbit általánosítása. Egy paritásbit minden egybites hibát észrevesz, a CRC-32 minden legfeljebb 32 bites „hibasorozatot”. Az Adler-32 gyorsabb, de gyengébb.
:::

```rust
//! Saját PNG-író. Nem tömörít, de szabványos fájlt ír, amit minden képnézegető megnyit.

use crate::canvas::Canvas;

/// CRC-32: a PNG darabjainak ellenőrzőösszege. Bitenként számoljuk, táblázat nélkül.
pub fn crc32(data: &[u8]) -> u32 {
    let mut crc = 0xFFFF_FFFF_u32;
    for &byte in data {
        crc ^= byte as u32;
        for _ in 0..8 {
            if crc & 1 == 1 {
                crc = (crc >> 1) ^ 0xEDB8_8320;
            } else {
                crc >>= 1;
            }
        }
    }
    !crc
}

/// Adler-32: a zlib-folyam ellenőrzőösszege.
pub fn adler32(data: &[u8]) -> u32 {
    let (mut a, mut b) = (1_u32, 0_u32);
    for &byte in data {
        a = (a + byte as u32) % 65_521;
        b = (b + a) % 65_521;
    }
    (b << 16) | a
}

/// Egy PNG-darab (chunk): hossz, négybetűs típus, adat, és a típus+adat CRC-je.
fn chunk(out: &mut Vec<u8>, kind: &[u8; 4], data: &[u8]) {
    out.extend_from_slice(&(data.len() as u32).to_be_bytes());
    let start = out.len();
    out.extend_from_slice(kind);
    out.extend_from_slice(data);
    let crc = crc32(&out[start..]);
    out.extend_from_slice(&crc.to_be_bytes());
}

/// zlib-folyam „tárolt” (tömörítetlen) deflate-blokkokból: blokkonként legfeljebb 65 535 bájt.
fn zlib_stored(raw: &[u8]) -> Vec<u8> {
    let mut out = vec![0x78, 0x01];
    let blocks: Vec<&[u8]> = raw.chunks(65_535).collect();
    for (i, block) in blocks.iter().enumerate() {
        // 1 bájt fejléc: az utolsó blokkban 1 (BFINAL), a típus 00 (tárolt)
        out.push(u8::from(i + 1 == blocks.len()));
        let len = block.len() as u16;
        out.extend_from_slice(&len.to_le_bytes());
        out.extend_from_slice(&(!len).to_le_bytes());
        out.extend_from_slice(block);
    }
    out.extend_from_slice(&adler32(raw).to_be_bytes());
    out
}

/// A vászon PNG-fájlként: 8 bites RGB, soronként egy 0-s szűrőbájttal.
pub fn encode(canvas: &Canvas) -> Vec<u8> {
    let mut raw = Vec::with_capacity((canvas.width * 3 + 1) * canvas.height);
    for row in canvas.pixels.chunks(canvas.width) {
        raw.push(0); // szűrő: nincs
        for &p in row {
            raw.extend_from_slice(&[(p >> 16) as u8, (p >> 8) as u8, p as u8]);
        }
    }
    let mut ihdr = Vec::new();
    ihdr.extend_from_slice(&(canvas.width as u32).to_be_bytes());
    ihdr.extend_from_slice(&(canvas.height as u32).to_be_bytes());
    // 8 bit csatornánként, RGB, deflate, 0-s szűrőmód, nincs átfésülés
    ihdr.extend_from_slice(&[8, 2, 0, 0, 0]);

    let mut out = b"\x89PNG\r\n\x1a\n".to_vec();
    chunk(&mut out, b"IHDR", &ihdr);
    chunk(&mut out, b"IDAT", &zlib_stored(&raw));
    chunk(&mut out, b"IEND", &[]);
    out
}
```

:::why Miért nem tömörít a mi PNG-írónk?
A deflate tömörítés két részből áll. Az **LZ77** megkeresi az ismétlődő bájtsorozatokat, és visszautalásra cseréli őket („ugyanaz a 300 bájt, mint 960 bájttal korábban”: egy egyszínű háttérnél ez rengeteg). A **Huffman-kódolás** a gyakori bájtoknak rövidebb bitkódot ad. Egy weboldal képernyőképe ettől jellemzően a huszadára zsugorodik.

A profi oldalon a `png` crate (és alatta a `miniz_oxide` vagy a `zlib-rs`) ezt mind tudja. Ha kedvet kapsz hozzá, egy egyszerű, csak LZ77-et használó tömörítő is nagyot javítana: a 0-s szűrő helyett a 2-es („a fenti sortól való eltérés”) egyszínű területen csupa nullát ad, amit az LZ77 nagyon jól tömörít.
