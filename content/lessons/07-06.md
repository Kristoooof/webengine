## Karakterből glif

Eddig a teszt mondta meg, hogy az `A` a 36-os glif. A böngészőben viszont szövegünk van, karakterekkel. A `cmap` tábla köti össze a kettőt.

Egy fontban több `cmap`-**altábla** is lehet, különböző platformokra és kódolásokra. A tábla elején egy lista áll: platform, kódolás, és hol kezdődik az altábla. A DejaVu Sansban:

| Platform | Kódolás | Formátum | Mire |
|---|---|---|---|
| 0 (Unicode) | 3 | 4 | Unicode, az első 65 536 karakter (BMP) |
| 0 (Unicode) | 10 | 12 | Unicode, minden karakter (emoji is) |
| 1 (Macintosh) | 0 | 6 | a régi Mac Roman kódolás, 256 karakter |
| 3 (Windows) | 1 | 4 | Unicode BMP (ugyanaz az altábla, mint az első) |
| 3 (Windows) | 10 | 12 | teljes Unicode |

Mi a (3, 1) vagy a (0, 3) altáblát keressük, és csak akkor, ha **4-es formátumú**. Szinte minden TrueType-fontban van ilyen.

## A 4-es formátum: szakaszok

A Unicode-ban a karakterek csoportokban vannak: az angol ábécé, a latin ékezetesek, a görög betűk … A 4-es formátum ezt használja ki: a kódtartományt **szakaszokra** (segment) osztja, és minden szakaszhoz egy szabályt ad. A DejaVu Sans első szakaszai:

| # | Kezdet | Vég | Eltolás (delta) | Példa |
|---|---|---|---|---|
| 0 | U+0000 | U+0000 | 0 | |
| 1 | U+0020 | U+007E | −29 | `A` = 65 → 65 − 29 = **36** |
| 2 | U+00A0 | U+02E9 | −62 | `ő` = 337 → 337 − 62 = **275** |
| … | | | | |
| 242 | U+FFFF | U+FFFF | 1 | (kötelező záró szakasz) |

Egy szakaszon belül a glif sorszáma egyszerűen `kód + eltolás`. A DejaVu Sans 243 szakasszal leírja mind a 6000-nél több karakterét.

Ha egy szakaszban a glifek nem egymás után következnek, a szabály más: a **range offset** egy külön glif-tömbre mutat, és a glif onnan olvasható ki. A DejaVu Sans ezt sosem használja, de más fontok igen.

Az altábla felépítése (minden mező `u16`):

```text Ábra
 0  format = 4
 2  length, language
 6  segCountX2          ← a szakaszok száma kétszer (!)
 8  searchRange, entrySelector, rangeShift
14  endCode[n]          ← a szakaszok vége, növekvő sorrendben
    reservedPad
    startCode[n]        ← a szakaszok eleje
    idDelta[n]          ← az eltolások
    idRangeOffset[n]    ← 0, vagy hivatkozás a glif-tömbre
    glyphIdArray[…]
```

A tömbök egymás után jönnek, mindegyik `n` elemű, és az `endCode` után van egy kitöltő `u16`. A helyüket ebből egyszerű kiszámolni.

### A keresés

1. **Bináris kereséssel** megkeressük az első szakaszt, aminek a **vége** ≥ a kód. (A végek növekvő sorrendben vannak.)
2. Ha a szakasz **eleje** > a kód, a karakter két szakasz közé esik: nincs a fontban.
3. Ha a `range offset` 0: a glif `kód + delta`.
4. Különben: a glif a `range offset` **saját helyétől** `range_offset + 2 · (kód − eleje)` bájtra van. Ha az 0, nincs glif, különben `glif + delta`.

Az összeadás **65 536-tal maradékosan** (modulo) értendő: a −29-es eltolás valójában `u16`-ként 65 507, és `65 + 65 507 = 65 572`, ami maradékosan 36. Rustban ez a `wrapping_add`.

:::compare Bináris keresés máshol
@@ C#
`Array.BinarySearch(endCodes, code)`: ha nincs pontos találat, negatív számot ad, aminek a komplemense (`~i`) az első nagyobb elem helye. Pont ez kell nekünk.
@@ C++
`std::lower_bound(ends.begin(), ends.end(), code)`: az első elem, ami nem kisebb a kódnál.
@@ Python
`bisect.bisect_left(ends, code)` ugyanezt adja.
@@ Rust
A szeleteknek van `partition_point` metódusa: `ends.partition_point(|&e| e < code)`. Mi most a fájlból olvassuk a végeket, nem egy szeletből, ezért kézzel írjuk meg.
@@ Érettségi
Ez a klasszikus logaritmikus keresés, egy kis csavarral: nem egy elemet keresünk, hanem az első olyat, ami ≥ a keresett érték. A `lo` és `hi` határok közt mindig a „még lehetséges” tartomány van.
:::

mod tests {
    use super::*;
    use crate::DEJAVU_SANS;

    // 07-06
    #[test]
    fn characters_to_glyphs() {

        assert_eq!(font.glyph_index('A'), 36);

        assert_eq!(font.glyph_index('ő'), 275);
        assert_eq!(font.glyph_index('Ő'), 274);

            "magánhasználatú karakter: nincs a fontban"

    fn range_offsets() {
        // Egy kézzel írt altábla: 'a'–'c' a glif-tömbből, és a kötelező záró 0xFFFF.
        let mut words: Vec<u16> = vec![4, 38, 0, 4, 0, 0, 0]; // fejléc, 2 szakasz
        words.extend([0x63, 0xFFFF]); // a szakaszok vége
        words.push(0); // kitöltés
        words.extend([0x61, 0xFFFF]); // a szakaszok eleje
        words.extend([5, 1]); // eltolások (delta)
        words.extend([4, 0]); // range offset: az első 4 bájttal előrébb, a glif-tömbre mutat

        let data: Vec<u8> = words.iter().flat_map(|w| w.to_be_bytes()).collect();
        assert_eq!(lookup(&data, 0, 'a'), Some(15), "10 + 5");
        assert_eq!(lookup(&data, 0, 'b'), None);
        assert_eq!(lookup(&data, 0, 'c'), Some(25));
        assert_eq!(lookup(&data, 0, 'd'), None, "két szakasz közé esik");
    }

A második teszt egy **kézzel írt** altáblát olvas. A DejaVu Sans sosem használ range offsetet, ezért ezt az ágat csak így tudjuk kipróbálni. Érdemes ehhez hasonló apró, „mesterséges” bemeneteket írni mindenhez, amit a valódi adat nem fed le.

:::hint
A `find_format4`-ben a `matches!` makró egy mintát illeszt, és `bool`-t ad: `matches!((platform, encoding), (3, 1) | (0, 3))`. A `|` itt „vagy” a minták között.
---
A `lookup` elején egy closure rövidíti a sok olvasást:
```rust
let at = |pos: usize| Reader::at(data, pos).u16();
let segments = at(sub + 6)? as usize / 2;
let ends = sub + 14;
let starts = ends + 2 * segments + 2;
```
A `+ 2` a kitöltő `u16` az `endCode` után. Ugyanígy jön utána a `deltas` és a `range_offsets`.
---
A bináris keresés: `lo = 0`, `hi = segments`, és amíg `lo < hi`, a közép (`mid`) végét nézed. Ha az kisebb a kódnál, a keresett szakasz jobbra van (`lo = mid + 1`), különben a `mid` maga is lehet az (`hi = mid`). A végén a `lo` az első jó szakasz, vagy `segments`, ha nincs ilyen.
---
A range offset hivatkozása a **saját helyéhez** képest számít. Ezért kell megjegyezni, hol olvastad: `let offset_pos = range_offsets + 2 * lo;`, és a glif helye `offset_pos + range_offset + 2 * (code - start) as usize`.
:::

:::solution
```rust
//! A `cmap` tábla: melyik karakterhez melyik glif tartozik.

use crate::reader::Reader;
use crate::{Font, Table};

/// A Windows Unicode (3, 1) vagy a Unicode (0, 3) altábla kezdete, ha 4-es formátumú.
pub fn find_format4(data: &[u8], cmap: Table) -> Option<usize> {
    let mut r = Reader::at(data, cmap.offset + 2);
    let count = r.u16()?;
    for _ in 0..count {
        let platform = r.u16()?;
        let encoding = r.u16()?;
        let start = cmap.offset + r.u32()? as usize;
        if matches!((platform, encoding), (3, 1) | (0, 3)) && Reader::at(data, start).u16()? == 4 {
            return Some(start);
        }
    }
    None
}

impl Font<'_> {
    /// A karakter glifje. A 0 a `.notdef` („tofu”): ilyen karakter nincs a betűtípusban.
    pub fn glyph_index(&self, c: char) -> u16 {
        self.cmap
            .and_then(|sub| lookup(self.data, sub, c))
            .unwrap_or(0)
    }
}

/// A 4-es formátum: szakaszok (start..=end), mindegyikhez egy eltolás (delta), vagy egy
/// hivatkozás egy külön glif-tömbre (range offset). A `sub` az altábla kezdete.
fn lookup(data: &[u8], sub: usize, c: char) -> Option<u16> {
    let code = u16::try_from(c as u32).ok()?; // a 4-es formátum csak az első 65 536 karaktert tudja
    let at = |pos: usize| Reader::at(data, pos).u16();
    let segments = at(sub + 6)? as usize / 2;
    let ends = sub + 14;
    let starts = ends + 2 * segments + 2;
    let deltas = starts + 2 * segments;
    let range_offsets = deltas + 2 * segments;

    // Az első szakasz, aminek a vége ≥ a kód. A végek növekvő sorrendben vannak: bináris keresés.
    let (mut lo, mut hi) = (0, segments);
    while lo < hi {
        let mid = (lo + hi) / 2;
        if at(ends + 2 * mid)? < code {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    if lo == segments {
        return None;
    }
    let start = at(starts + 2 * lo)?;
    if code < start {
        return None;
    }
    let delta = at(deltas + 2 * lo)?;
    let offset_pos = range_offsets + 2 * lo;
    let range_offset = at(offset_pos)? as usize;
    let glyph = if range_offset == 0 {
        code
    } else {
        // A hivatkozás a saját helyéhez képest számít: ezért kell az `offset_pos`.
        let g = at(offset_pos + range_offset + 2 * (code - start) as usize)?;
        if g == 0 {
            return None;
        }
        g
    };
    Some(glyph.wrapping_add(delta))
}
```

Most írd át a korábbi teszteket, hogy karakterrel kérjék a glifet! Például a `the_letter_r`-ben `font.rasterize(53, 24.0)` helyett `font.rasterize(font.glyph_index('R'), 24.0)`. Ez nem kötelező (a referencia-megoldás meghagyja a számokat, megjegyzéssel), de olvashatóbb.

:::why Mélyvíz: a 12-es formátum és az emoji
A 4-es formátum `u16` kódokat ismer, vagyis csak a Unicode első 65 536 karakterét, a **BMP**-t (Basic Multilingual Plane). Az emoji (pl. 😀 = U+1F600) és sok ritka írásjel ezen kívül van. Ezekhez a **12-es formátum** kell: ott a szakaszok 32 bitesek, és a szabály még egyszerűbb (`kezdő glif + (kód − eleje)`).

A DejaVu Sansban van 12-es altábla is, de emoji nincs benne. A böngészők ilyenkor **font fallback**-et csinálnak: ha egy karakter nincs meg az oldal betűtípusában, keresnek egy másik fontot a rendszerben, amiben megvan (Windowson a Segoe UI Emoji-t). Ez a 16. modulban, a profi szövegmotornál jön elő.
:::
