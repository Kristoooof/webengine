## Trait: közös viselkedés

A **trait** leírja, mit kell tudnia egy típusnak, de azt nem, hogyan. Pont olyan, mint a C#-os `interface`:

```rust
pub trait Tokenizer {
    fn name(&self) -> &'static str;
    fn tokenize(&self, input: &str) -> Vec<Token>;
}
```

Egy típus így **valósítja meg** (implementálja):

```rust
pub struct NaiveTokenizer;     // "unit struct": nincs mezője, csak viselkedése

impl Tokenizer for NaiveTokenizer {
    fn name(&self) -> &'static str {
        "naiv"
    }

    fn tokenize(&self, input: &str) -> Vec<Token> {
        // ...
    }
}
```

:::note Mi az a `&'static str`?
Egy olyan `&str`, ami a program **teljes futása alatt** érvényes. A szöveg-literálok (`"naiv"`) ilyenek, mert be vannak égetve a futtatható fájlba. A `'static` egy *lifetime*: ez az egyetlen eset, amikor most ki kell írni.
:::

### Alapértelmezett metódus

A traitben lehet alapértelmezett megvalósítás is, amit az implementáló típus felülírhat:

```rust
pub trait Tokenizer {
    fn name(&self) -> &'static str;
    fn tokenize(&self, input: &str) -> Vec<Token>;

    fn count_tags(&self, input: &str) -> usize {
        self.tokenize(input)
            .iter()
            .filter(|t| matches!(t, Token::StartTag { .. } | Token::EndTag { .. }))
            .count()
    }
}
```

## Trait használata: kétféleképpen

### 1. Generikusan (fordítási időben dől el)

```rust
fn show<T: Tokenizer>(t: &T, input: &str) {
    println!("{}: {:?}", t.name(), t.tokenize(input));
}
// rövidebben, ugyanaz:
fn show(t: &impl Tokenizer, input: &str) { /* ... */ }
```

A fordító **minden típushoz külön példányt** készít ebből a függvényből (*monomorfizáció*). Ez nagyon gyors, de fordításkor kell tudni, melyik típusról van szó.

### 2. Dinamikusan (futásidőben dől el): `dyn Trait`

```rust
pub fn pick(naive: bool) -> Box<dyn Tokenizer> {
    if naive {
        Box::new(NaiveTokenizer)
    } else {
        Box::new(CursorTokenizer)    // ezt a következő leckében írod meg
    }
}

let t = pick(true);
println!("{}", t.name());
```

- A `dyn Tokenizer` jelentése: *„valami, ami Tokenizer, de nem tudjuk, pontosan mi”*.
- A `Box<...>` a heapre teszi. Erre azért van szükség, mert a különböző implementációk különböző méretűek lehetnek, a `Box` viszont mindig egy mutató méretű.
- Híváskor egy **virtuális táblán** (vtable) keresztül derül ki, melyik kód fusson. Pont úgy, mint C#-ban egy interfész-hívásnál vagy C++-ban egy `virtual` függvénynél.

**Ez a nagy kapcsoló.** A böngésző beállításaiban egy checkbox, és a `Box<dyn HtmlParser>` mögött hol a te parsered, hol a html5ever fut.

:::compare
@@ C#
```csharp
interface ITokenizer { string Name { get; } List<Token> Tokenize(string input); }
class NaiveTokenizer : ITokenizer { ... }
ITokenizer t = naive ? new NaiveTokenizer() : new CursorTokenizer();
```
@@ C++
```cpp
struct Tokenizer { virtual std::vector<Token> tokenize(std::string_view) = 0; };
struct NaiveTokenizer : Tokenizer { ... };
std::unique_ptr<Tokenizer> t = naive ? std::make_unique<NaiveTokenizer>() : ...;
```
@@ Rust
```rust
trait Tokenizer { fn tokenize(&self, input: &str) -> Vec<Token>; }
struct NaiveTokenizer;
impl Tokenizer for NaiveTokenizer { ... }
let t: Box<dyn Tokenizer> = if naive { Box::new(NaiveTokenizer) } else { ... };
```
A `Box<dyn Trait>` a C++ `unique_ptr<Base>` megfelelője.
:::

## Standard traitek: Display

A standard könyvtár tele van traitekkel. Az egyik leghasznosabb a `Display`: ez mondja meg, hogyan jelenjen meg egy érték a `{}`-ben (a `Debug` a `{:?}`-ben).

```rust
use std::fmt;

impl fmt::Display for Token {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Token::StartTag { name, self_closing: true } => write!(f, "<{name}/>"),
            Token::StartTag { name, .. } => write!(f, "<{name}>"),
            Token::EndTag { name } => write!(f, "</{name}>"),
            Token::Text(t) => write!(f, "{t}"),
            Token::Comment(c) => write!(f, "<!--{c}-->"),
        }
    }
}
```

A `write!` olyan, mint a `format!`, csak a formatterbe ír. Ha a `Display` megvan, ingyen kapsz egy `.to_string()` metódust is, mert a standard könyvtár minden `Display` típushoz megírja.

Más gyakori standard traitek, amikkel találkozni fogsz:

| Trait | Mit ad | Példa |
|---|---|---|
| `Debug` | `{:?}` | `#[derive(Debug)]` |
| `Display` | `{}` és `.to_string()` | kézzel kell megírni |
| `Clone` | `.clone()` | `#[derive(Clone)]` |
| `PartialEq` | `==` | `#[derive(PartialEq)]` |
| `Default` | `T::default()` | üres/alapérték |
| `From` / `Into` | `T::from(x)` / `x.into()` | átalakítás. Ezért működött a `"p".into()`! |

```rust
let mut tokens = Vec::new();
```

A ciklusmagban egy szép trükk: `match`-elj egyszerre két értékre egy tuple-lel!
```rust
match (c, inside_tag) {

}
```

---
A `('<', false)` ágban: ha a `buf` nem üres, `tokens.push(Token::Text(buf.clone()))`, és `buf.clear()`. Utána `buf.push(c)` (a `<` a tag része), és `inside_tag = true`. A `('>', true)` ágban: `buf.push(c)`, majd `tokens.push(Token::from_tag(Tag::parse(&buf)))`, `buf.clear()`, `inside_tag = false`.

:::solution
```rust
// src/tokenizer.rs
use crate::tag::Tag;
use crate::token::Token;

pub trait Tokenizer {
    fn name(&self) -> &'static str;
    fn tokenize(&self, input: &str) -> Vec<Token>;
}

pub struct NaiveTokenizer;

impl Tokenizer for NaiveTokenizer {
    fn name(&self) -> &'static str {
        "naiv"
    }

    fn tokenize(&self, input: &str) -> Vec<Token> {
        let mut tokens = Vec::new();
        let mut buf = String::new();
        let mut inside_tag = false;
        for c in input.chars() {
            match (c, inside_tag) {
                ('<', false) => {
                    if !buf.is_empty() {
                        tokens.push(Token::Text(buf.clone()));
                        buf.clear();
                    }
                    buf.push(c);
                    inside_tag = true;
                }
                ('>', true) => {
                    buf.push(c);
                    tokens.push(Token::from_tag(Tag::parse(&buf)));
                    buf.clear();
                    inside_tag = false;
                }
                _ => buf.push(c),
            }
        }
        if !buf.is_empty() {
            tokens.push(Token::Text(buf));
        }
        tokens
    }
}

pub fn pick(_naive: bool) -> Box<dyn Tokenizer> {
    Box::new(NaiveTokenizer)
}
```

:::why Statikus vagy dinamikus? Mikor melyik?
A **generikus** (`impl Trait`, `<T: Trait>`) gyorsabb, mert a fordító beépítheti (inline) a hívást, de minden típushoz új kódot generál, és fordításkor el kell dőlnie. A **dinamikus** (`dyn Trait`) egy picit lassabb (indirekt hívás), de futásidőben váltható, és egy `Vec<Box<dyn Trait>>`-ben különböző típusok is lehetnek. A Rozsdában a kapcsolóhoz `dyn`-t használunk. Egy HTML-parse egyszer fut le oldalanként, ott az a pár nanoszekundum nem számít. Egy belső ciklusban (pl. pixelenként) viszont a generikus a jobb.

:::card
K: Mi a különbség az `impl Trait` és a `dyn Trait` között?
V: Az `impl Trait` statikus: fordításkor dől el a típus, és minden típushoz külön kód készül (gyors). A `dyn Trait` dinamikus: futásidőben választható, vtable-ön keresztül hívódik (rugalmas).
:::

:::card
K: Mit ad a `Display` trait megvalósítása?
V: Hogy az érték kiírható legyen `{}`-vel, és ingyen kapsz egy `.to_string()` metódust is.
:::

:::card
K: Miért kell `Box` a `dyn Trait` köré?
V: Mert a különböző implementációk különböző méretűek lehetnek. A `Box` a heapre teszi az értéket, és fix méretű mutatót ad.
