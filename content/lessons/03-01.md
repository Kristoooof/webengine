## Miért kell szabvány?

1995 körül minden böngésző másképp értelmezte a hibás HTML-t, és a weboldalak böngészőnként másképp néztek ki. A **HTML5** (2008–2014) nagy újítása az volt, hogy pontosan leírta, **hogyan kell parse-olni bármilyen bemenetet**, a hibásat is. Azóta minden böngésző karakterre pontosan ugyanazt a fát építi.

A szabvány neve **HTML Living Standard**, a WHATWG gondozza, és folyamatosan frissül:
[html.spec.whatwg.org/multipage/parsing.html](https://html.spec.whatwg.org/multipage/parsing.html)

:::adhd Ne olvasd el az egészet!
A parsing fejezet több száz oldal. Senki nem olvassa végig, a böngészőfejlesztők sem. Úgy használják, mint egy szótárt: megkeresik a szükséges állapotot vagy szabályt, elolvassák, megírják. Ma csak egyetlen kis részt fogsz elolvasni.
:::

## A parsing modell

  <div class="pl-step"><b>2</b><strong>Dekódolás</strong><small>bájtok → karakterek (UTF-8)</small></div>
  <div class="pl-step"><b>3</b><strong>Előfeldolgozás</strong><small>sorvégek egységesítése</small></div>
  <div class="pl-step"><b>4</b><strong>Tokenizer</strong><small>állapotgép → tokenek</small><em>03-02 – 03-06</em></div>

A 2. lépést a Rust megcsinálja helyetted: a `std::fs::read_to_string` UTF-8-ként olvas. A 3. lépést most írod meg, a 4. és az 5. a modul fő része.

### Előfeldolgozás: a sorvégek

A Windows a sorvéget két karakterrel jelöli (`\r\n`, CRLF), a Linux és a macOS eggyel (`\n`, LF), a régi Mac-ek pedig `\r`-rel (CR). A szabvány előírja, hogy a tokenizer előtt **minden sorvég LF legyen**. Így a tokenizernek csak egyféle sorvéggel kell foglalkoznia.

## Hogyan olvass egy állapotot?

Íme a legfontosabb állapot, a **Data state** (13.2.5.1), magyarul, kicsit egyszerűsítve:

> **Adat állapot.** Fogyaszd el a következő bemeneti karaktert:
> - **U+0026 AMPERSAND (&):** állítsd a visszatérési állapotot az adat állapotra, és válts a karakterhivatkozás állapotra.
> - **U+003C LESS-THAN SIGN (<):** válts a tag nyitása állapotra.
> - **U+0000 NULL:** ez parse error. Bocsásd ki az aktuális bemeneti karaktert karakter-tokenként.
> - **EOF:** bocsáss ki egy fájlvége-tokent.
> - **Bármi más:** bocsásd ki az aktuális bemeneti karaktert karakter-tokenként.

A szabvány minden állapota ugyanígy épül fel: elolvasunk egy karaktert, és egy lista eldönti, mi történjen. Pont ez egy `match` a Rustban! A szabvány szavai, és amit a kódban jelentenek:

| A szabványban | Jelentés | A kódunkban |
|---|---|---|
| *Consume the next input character* | Olvasd be a következő karaktert | `let c = self.next_char();` |
| *Switch to the X state* | A következő karaktert az X állapot kezeli | `self.state = State::X;` |
| *Reconsume in the X state* | Válts X-re, és **ugyanezt** a karaktert dolgozd fel újra | `self.reconsume(); self.state = State::X;` |
| *Emit the current token* | Add ki a tokent | `self.emit(...)` |
| *This is a parse error* | A bemenet hibás, de **nem állunk meg**, a szabvány leírja, hogyan folytassuk | (legfeljebb naplózzuk) |
| *EOF* | Elfogyott a bemenet | `None` |

:::note A parse error nem hiba
Egy C#-fordító megáll a szintaktikai hibánál. A böngésző **soha**. A „parse error” csak annyit jelent, hogy egy validátor szólna, a parser viszont pontosan előírt módon folytatja. Ezért nem lehet a HTML-ben „szintaktikai hibát” csinálni, ami miatt nem jelenik meg az oldal.
:::

## Az új tokenizer váza

Az új tokenizer a `rozsda-html` crate-ben egy **új modulba** kerül: `src/lexer.rs`. A régi `tokenizer.rs` a modul végéig marad, hogy a Rozsda 0.1 közben is működjön. A 03-11-es leckében cseréljük le.

Az új `Token` típus a szabványt követi:

```rust
#[derive(Debug, Clone, PartialEq)]
pub struct Attribute {
    pub name: String,
    pub value: String,
}

#[derive(Debug, Clone, PartialEq)]
pub enum Token {
    Doctype { name: String },
    StartTag { name: String, attrs: Vec<Attribute>, self_closing: bool },
    EndTag { name: String },
    Comment(String),
    Text(String),
    Eof,
}
```

Két különbség a régihez képest: a kezdőtag most már **megtartja az attribútumokat**, és van külön **`Eof`** (fájlvége) token. A fa-építőnek tudnia kell, mikor ért véget a bemenet, mert akkor zárja le a nyitva maradt elemeket.

:::why Karakter-tokenek vagy szöveg-tokenek?
A szabvány minden karaktert külön tokenként bocsát ki („emit the current input character as a character token”), a fa-építő pedig a szomszédos karaktereket összefűzi egy szövegcsomópontba. Mi ezt a lépést előrehozzuk: a tokenizer gyűjti a karaktereket, és egy `Text(String)` tokent ad ki. Kívülről nézve az eredmény ugyanaz, csak sokkal kevesebb token keletkezik. A html5ever (a Servo parsere) is hasonló trükköt használ.
:::

```rust test
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn preprocess_newlines() {
        assert_eq!(preprocess("a\r\nb\rc\nd"), "a\nb\nc\nd");
        assert_eq!(preprocess(""), "");
    }
}
```

:::hint
A `str::replace` egy új `String`-et ad vissza, így láncolható: `input.replace(..).replace(..)`.
---
A sorrend számít! Ha **előbb** cseréled a `\r`-t `\n`-re, a `\r\n`-ből `\n\n` lesz, két sortörés egy helyett. Előbb a kétkarakteres `"\r\n"` → `"\n"` csere jöjjön, utána a maradék `'\r'` → `"\n"`.
:::

:::solution
```rust
//! HTML-tokenizer a WHATWG-szabvány 13.2.5 fejezete alapján (egyszerűsítve).

/// A bemenet előfeldolgozása: minden sorvég (CRLF, CR) LF lesz.
pub fn preprocess(input: &str) -> String {
    input.replace("\r\n", "\n").replace('\r', "\n")
}
```
:::
