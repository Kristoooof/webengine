A CSS-motor megtanulja a doboz tulajdonságait: `margin-*`, `padding-*`, `border-*-width`, `border-style`, `border-color`, `width` és `height`. Megtudod, miért marad meg a százalék és az `auto` a layoutig, mit jelent az `em` egy margónál, és miért 0 a keret vastagsága, ha nincs `border-style`.

| Tulajdonság | Értékek | Kezdőérték | Öröklődik? |

:::note Egyszerűsítések
A szabványban a `border-style` és a `border-color` is oldalanként külön állítható (`border-left-style`…). Mi egy-egy értéket tárolunk mind a négy oldalra. A `dashed`, a `dotted` és a társaik nálunk is érvényesek, de folytonos vonalként rajzoljuk őket (a 6. modulban szépíthetsz rajta).
:::

## Mikor lesz a százalékból pixel?

Az `em` a stílusszámításnál már pixellé válik, a százalék viszont **nem**. A `width: 50%` a **tartalmazó blokk** (containing block) szélességének a fele, azt pedig csak a layout tudja: egy `div` szélessége függ a szülője szélességétől, az pedig az ablak méretétől. Ezért a számított érték egy háromféle méret:

```rust
/// Egy méret: pixel, százalék (amit csak a layout tud pixelre váltani) vagy `auto`.
#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Size {
    Px(f32),
    Percent(f32),
    Auto,
}
```

Az `auto` sem szám: azt jelenti, hogy „döntse el a layout-algoritmus”. Egy blokk `auto` szélessége kitölti a helyet, az `auto` margók pedig középre igazítanak (05-05). A `resolve` metódus a layoutnak segít: pixelt ad, a százalékot egy alaphoz mérve, az `auto`-ra pedig `None`-t.

:::compare Meglepő százalékok
@@ CSS
A `padding-top: 10%` és a `margin-top: 10%` a tartalmazó blokk **szélességének** 10%-a, nem a magasságáé! Ez a szabvány tudatos döntése: így a négy oldal ugyanahhoz az alaphoz mér, és a magasság (ami a tartalomtól függ) nem okoz körbe-függést. Régen ezzel a trükkel csináltak fix oldalarányú dobozokat (`padding-top: 56.25%` → 16:9).
@@ Érettségi
Ugyanaz, mint egy százalékszámítás-feladat: a „mennyi a 30%” kérdésre csak akkor tudsz válaszolni, ha tudod, *minek* a 30%-a. A CSS-ben az „alap” a tartalmazó blokk szélessége.
:::

## Az `em` új jelentése

A 04-10-ben a `font-size: 2em` a **szülő** betűméretéhez mért. Minden más tulajdonságnál az `em` az elem **saját** (már kiszámolt) betűméretéhez mér. A `h1 { font-size: 2em; margin: 0.67em 0 }` esetén:

1. Előbb a betűméret: 2 · 16 = **32px**.
2. Aztán a margó: 0,67 · **32** = **21,44px**.

Ezért kell a `compute`-ban a betűméretet a doboz-tulajdonságok **előtt** kiszámolni. A mértékegység nélküli `0` is érvényes hossz (`margin: 0`), de más mértékegység nélküli szám nem: a `margin: 5` érvénytelen.

## Keret stílus nélkül: nincs keret

```css
div { border-width: 10px; }
```

Látszik keret? **Nem.** A `border-style` kezdőértéke `none`, és a szabvány szerint ilyenkor a keret **számított vastagsága 0**, akármit írt is a szerző. Ezért kell a gyakorlatban mindig mindhármat megadni: `border: 2px solid red`. A keret színe alapból `currentcolor`, vagyis az elem szövegének színe.

/// Egy hossz pixelben. A `font-size`-on kívül az `em` az elem SAJÁT betűméretéhez mér.
pub fn length_px(value: &Value, font_size: f32) -> Option<f32> {
    match value {
        Value::Length(n, Unit::Px) => Some(*n),
        Value::Length(n, Unit::Em) => Some(n * font_size),
        Value::Length(n, Unit::Rem) => Some(n * 16.0),
        Value::Number(n) if *n == 0.0 => Some(0.0),
        _ => None,
    }
}

/// Margó, kitöltés, szélesség, magasság: a százalék és az `auto` a layoutig megmarad.
pub fn size(value: &Value, font_size: f32) -> Size {
    match value {
        Value::Percentage(p) => Size::Percent(*p),
        Value::Keyword(k) if k == "auto" => Size::Auto,
        v => length_px(v, font_size).map_or(Size::Auto, Size::Px),
    }
}

pub fn border_width_px(value: &Value, font_size: f32) -> f32 {
    match value {
        Value::Keyword(k) if k == "thin" => 1.0,
        Value::Keyword(k) if k == "medium" => 3.0,
        Value::Keyword(k) if k == "thick" => 5.0,
        v => length_px(v, font_size).unwrap_or(0.0),
    }
}

:::why Miért nem egy nagy `HashMap` a számított stílus?
A böngészőkben több száz CSS-tulajdonság van. Csábító lenne a számított stílust is egy `HashMap<String, Value>`-ként tárolni, ahogy a kaszkád eredményét. A Firefox stílusmotorja (Stylo) mégis structokat használ, tulajdonság-csoportonként (`Font`, `Border`, `Margin`…), és a csoportokat a hasonló elemek **megosztják** egymással (`Arc`-kal). Ennek két oka van. Egy struct mezőjét elérni egyetlen memóriaolvasás, egy `HashMap`-ben keresni hashelés és összehasonlítás. Ráadásul egy tipikus oldalon a legtöbb bekezdésnek pontosan ugyanolyan a margója és a betűje, így a megosztással rengeteg memória spórolható meg.

- [ ] 24px, mert az `em` a szülő 16px-es betűméretéhez mér
- [x] 30px, mert a `font-size`-on kívül az `em` az elem saját betűméretéhez mér
- [ ] 1,5px
> Az elem betűmérete 20px, a margó ennek másfélszerese: 30px. Csak a `font-size`-nál mér az `em` a szülőhöz, mert ott épp a sajátot számoljuk.
:::

:::quiz
Mit lát a felhasználó a `div { border-width: 5px; border-color: red }` esetén?
- [ ] 5 pixeles piros keretet
- [x] Semmilyen keretet: a `border-style` kezdőértéke `none`, és ilyenkor a keret vastagsága 0
- [ ] 3 pixeles fekete keretet
> Keret csak akkor van, ha a stílusa nem `none`. Ezért írjuk szinte mindig a rövidítést: `border: 5px solid red`.
:::

:::card
K: Miért marad meg a százalék a számított értékben, és mikor lesz belőle pixel?
V: Mert a tartalmazó blokk szélességétől függ, amit csak a layout ismer. A layout számolja ki (`Size::resolve`).
:::

:::card
K: Mihez mér az `em` a `margin`-nál, és mihez a `font-size`-nál?
V: A `margin`-nál (és minden más tulajdonságnál) az elem saját betűméretéhez, a `font-size`-nál a szülőéhez.
:::

:::win
- A CSS-motor ismeri a doboz-tulajdonságokat: margó, kitöltés, keret, szélesség, magasság.
- `Size`: pixel, százalék vagy `auto`, amíg a layout el nem dönti.
- Az `em` két jelentése, és a „keret stílus nélkül = nincs keret” szabály.
:::

:::next

:::
