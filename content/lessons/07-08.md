:::goal
Megtanítod a fontot **mérni**: mennyit lép előre a toll egy betű után (`hmtx`), és mely betűpárok kerüljenek közelebb egymáshoz (`kern`). Aztán a `rozsda-core`-ba kerül egy `FontMetrics` trait, amin keresztül a layout a következő leckében a betűtípust kérdezi. A lecke végén a `font.text_width("AV", 16.0)` pontosan annyi, mint egy igazi böngészőben.
:::

## Előrelépés: a `hmtx`

Egy glif rajza és a helye nem ugyanaz. Az `i` keskeny, de kell mellette egy kis hely; a szóköznek nincs rajza, mégis széles. Minden glifnek van egy **előrelépése** (advance width): ennyivel megy jobbra a toll, miután kirajzoltuk.

```text Ábra
          ┌─────────┐
          │    ╱╲   │
          │   ╱──╲  │
          │  ╱    ╲ │
 ─────────●─────────●───────── alapvonal
          toll      toll a következő betűhöz
          └─ előrelépés: 1401 egység (az „A”) ─┘
```

Az előrelépések a `hmtx` (horizontal metrics) táblában vannak. Az eleje `numberOfHMetrics` darab sor, mindegyik egy előrelépés (`u16`) és egy bal oldali rés (`i16`, ezt nem használjuk):

```text Ábra
hmtx:  [1229, 102] [0, 0] [682, 0] [651, 0] [821, 309] … [1401, 16] …   ← 4 bájtos sorok
         0. glif    1.     2.       3.       4. (!)        36. (A)
```

A `numberOfHMetrics` a `hhea` tábla 34. bájtján áll. Ha egy glif sorszáma ennél nagyobb, az előrelépése ugyanannyi, mint az **utolsó** soré. A fontok ezzel spórolnak, mert a végükön sokszor egyforma széles jelek vannak (a DejaVu Sansban 6253 glifből 6238-nak van saját sora).

## Alávágás (kerning): a `kern`

Ha minden betű a saját szélességével lép, az „AV” csúnya: az `A` jobb lába és a `V` bal szára között nagy rés tátong. A **kerning** (alávágás) erre egy javítás: betűpáronként egy kis (általában negatív) érték, ami közelebb húzza a párt.


A DejaVu Sansban 2727 ilyen pár van. Néhány, font-egységben (2048 = 1 em):

| Pár | Érték | 16px-en |
|---|---|---|
| A, V | −131 | −1,02 px |
| A, T | −159 | −1,24 px |
| T, o | −348 | −2,72 px |
| L, T | −282 | −2,20 px |

A régi `kern` tábla 0-s formátuma egyszerű: egy fejléc, aztán `(bal glif, jobb glif, érték)` hármasok (`u16`, `u16`, `i16`, 6 bájt), a két glif szerint **rendezve**. Ha a bal és a jobb glifet egy 32 bites számmá rakjuk össze (`bal << 16 | jobb`), a párok ennek a számnak a sorrendjében vannak, és bináris kereséssel kereshetők.

```text Ábra
kern:  verzió (u16)  altáblák száma (u16)
       altábla:  verzió  hossz  coverage   ← a coverage alsó bitje: vízszintes;
                                              a felső bájtja: a formátum (0)
                 nPairs  searchRange  entrySelector  rangeShift
                 [bal, jobb, érték] × nPairs
```

:::note GPOS: a modern kerning
Az újabb fontokban a kerning a `GPOS` (glyph positioning) táblában van: az sokkal többet tud (osztályokat, ékezetek pontos elhelyezését, arab és indiai írások szabályait), de sokkal bonyolultabb is. A DejaVu Sansban mindkettő megvan. A `GPOS` a profi szövegmotorok (HarfBuzz, Swash) dolga, a 16. modulban.
:::

## Mérés egy közös nyelven

A layoutnak (`rozsda-layout`) tudnia kell, milyen széles egy szó, és milyen magas egy sor. De nem kell tudnia, **honnan** jön ez: a 8×8-as bitkép-betűkből, a mi TrueType-olvasónkból, vagy a 16. modulban egy profi szövegmotorból. Ez a kapcsoló-architektúra lényege (lásd a `HtmlParser`, `StyleEngine`, `LayoutEngine` traitet): a közös nyelv a `rozsda-core`-ba kerül, és mindenki csak azt ismeri.

Új fájl a `rozsda-core`-ban: `src/text.rs` (és a `lib.rs`-ben `pub mod text;`):

```rust
//! Szövegmérés: a layout ebből tudja, milyen széles egy szó, és milyen magas egy sor.

/// Bármi, ami szöveget tud mérni. A betűméret (`size`) mindig pixelben van.
pub trait FontMetrics {
    /// A szöveg szélessége: a karakterek előrelépéseinek összege, alávágással együtt.
    fn text_width(&self, text: &str, size: f32) -> f32;

    /// Az alapvonal fölötti rész magassága.
    fn ascent(&self, size: f32) -> f32;

    /// Az alapvonal alatti rész magassága (pozitív szám).
    fn descent(&self, size: f32) -> f32;

    /// Egy sor magassága (`line-height: normal`).
    fn line_height(&self, size: f32) -> f32 {
        self.ascent(size) + self.descent(size)
    }

    /// Az aláhúzás távolsága az alapvonal alatt, és a vastagsága.
    fn underline(&self, size: f32) -> (f32, f32) {
        let thickness = (size / 14.0).max(1.0);
        (thickness, thickness)
    }
}
```

Az utolsó két metódusnak van **alapértelmezett** törzse: aki a traitet megvalósítja, csak a `text_width`-et, az `ascent`-et és a `descent`-et köteles megírni, a többit felülírhatja, ha akarja.

```rust
//! Méretek: mennyivel lép előre a toll egy glif után, és mennyivel kerülnek közelebb a párok.

use crate::reader::Reader;
use crate::{Font, Table};
use rozsda_core::text::FontMetrics;

/// A `kern` tábla első altáblájának párjai: (kezdet, darabszám). Csak a 0-s formátumot ismerjük.
pub fn find_kern_pairs(data: &[u8], kern: Table) -> Option<(usize, usize)> {
    let mut r = Reader::at(data, kern.offset);
    let _version = r.u16()?;
    if r.u16()? == 0 {
        return None; // nincs altábla
    }
    let _sub_version = r.u16()?;
    let _length = r.u16()?;
    let coverage = r.u16()?;
    let horizontal = coverage & 1 != 0;
    if coverage >> 8 != 0 || !horizontal {
        return None;
    }
    let pairs = r.u16()? as usize;
    r.skip(6); // searchRange, entrySelector, rangeShift
    Some((r.pos(), pairs))
}

impl Font<'_> {
    /// Egy glif előrelépése (advance width) font-egységben: ennyivel megy jobbra a toll.
    pub fn advance(&self, glyph: u16) -> u16 {
        // Az utolsó `num_h_metrics` utáni glifek mind az utolsó szélességét kapják (pl. kínai írásjelek).
        let i = glyph.min(self.num_h_metrics.saturating_sub(1)) as usize;
        self.u16_at(self.hmtx.offset + 4 * i).unwrap_or(0)
    }

    /// Az alávágás (kerning) két egymás utáni glif között, font-egységben. Negatív: közelebb.
    pub fn kerning(&self, left: u16, right: u16) -> i16 {
        self.find_kerning(left, right).unwrap_or(0)
    }

    /// A párok a (bal, jobb) szerint rendezve vannak: bináris keresés a 32 bites kulcson.
    fn find_kerning(&self, left: u16, right: u16) -> Option<i16> {
        let (start, count) = self.kern?;
        let key = ((left as u32) << 16) | right as u32;
        let (mut lo, mut hi) = (0, count);
        while lo < hi {
            let mid = (lo + hi) / 2;
            let mut r = Reader::at(self.data, start + 6 * mid);
            let pair = r.u32()?;
            if pair < key {
                lo = mid + 1;
            } else if pair > key {
                hi = mid;
            } else {
                return r.i16();
            }
        }
        None
    }

    fn px(&self, units: f32, size: f32) -> f32 {
        units * size / self.units_per_em as f32
    }
}

impl FontMetrics for Font<'_> {
    fn text_width(&self, text: &str, size: f32) -> f32 {
        let mut units = 0;
        let mut previous = None;
        for c in text.chars() {
            let glyph = self.glyph_index(c);
            if let Some(p) = previous {
                units += self.kerning(p, glyph) as i32;
            }
            units += self.advance(glyph) as i32;
            previous = Some(glyph);
        }
        self.px(units as f32, size)
    }

    fn ascent(&self, size: f32) -> f32 {
        self.px(self.ascender as f32, size)
    }

    fn descent(&self, size: f32) -> f32 {
        self.px(-self.descender as f32, size)
    }
}
```
:::

Figyeld meg a `find_kerning` trükkjét: a pár két `u16`-ját **egyetlen** `u32`-ként olvassuk ki (`r.u32()`), és ez pont a `bal << 16 | jobb` kulcs, mert a fájl big-endian. Utána ugyanaz a `Reader` olvassa tovább az értéket.

:::why Mélyvíz: a `line-height: normal`
A CSS alapértelmezett sormagassága, a `normal`, a fonttól függ: a böngészők az ascent + descent + lineGap összeget veszik. A DejaVu Sansnál a `lineGap` 0, ezért 16px-en 18,625 px egy sor. A Chrome és a Firefox ugyanezt számolja (néhány böngésző egész pixelre kerekít).

A valóságban három helyen is lehetnek ilyen számok: a `hhea` táblában (ezt használjuk), az `OS/2` tábla „typo” mezőiben és az `OS/2` „win” mezőiben. Hogy melyik számít, az platformonként és fontonként más, és ez a webfejlesztők egyik kedvenc rejtélye („miért magasabb a sor Windowson?”).
:::

```rust
fn text_width(advances: &[u16], kerning: &[(u16, u16, i16)], glyphs: &[u16]) -> i32 {
```
```rust
    let advance = |g: u16| advances[(g as usize).min(advances.len() - 1)] as i32;

        kerning
```
