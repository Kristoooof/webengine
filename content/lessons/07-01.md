## Búcsú a 8×8-as betűktől

A 2. modul óta a Rozsda **bitképes** (bitmap) betűkkel ír. Minden betű egy 8×8-as pixelrács, és nagyobb méretben egyszerűen kétszeres vagy háromszoros pixelekkel rajzoljuk ki. Ennek három baja van:

- **Csak egész nagyítás van.** A 16px-es szöveg 2×, a 20px-es is 2× (vagy 3×). A 18,72px-es `<h3>` ugyanakkora, mint a sima szöveg.
- **Minden betű egyforma széles.** Az `i` és az `M` is 8 egység, ami csúnya, és pazarolja a helyet.
- **Nincs ő és ű.** A font8x8-ban nincsenek benne, ezért `ö`-t és `ü`-t rajzolunk helyettük (02-05).

A mai betűtípusok **vektorosak**: egy betű nem pixelekből áll, hanem **körvonalakból** (outline). A körvonal pontok sorozata, a pontok között egyenesek és görbék futnak. Ezt bármekkora méretre fel lehet nagyítani, és a nagyítás után **raszterizáljuk**: kiszámoljuk, melyik pixelt mennyire fedi le az alakzat.

```text Ábra
  az „o” külső körvonala                16px-en raszterizálva (a 07-05 után)
  (font-egységben, 2048 = 1 em)

          ○    ●    ○                         .*%#+
      ○                 ○                    .%*--#%
                                             *%   .@=
     ●                   ●     ──────►       %*    %*
                                             @=    *#
      ○                 ○                    %+    ##
          ○    ●    ○                        #%   .@+
                                             :@= .*%.
  ● görbén lévő pont                          -%@@%:
  ○ vezérlőpont: a görbét „húzza”
```

:::compare Betűk máshol
@@ C#
A WPF és a WinForms a Windows betűmotorját (DirectWrite, régebben GDI) hívja: te csak egy `FontFamily`-t adsz meg, a többit a rendszer intézi. A `GlyphTypeface` osztály mutatja meg a mögötte lévő adatokat (glifek, metrikák).
@@ C++
A Linux-világ szabványa a **FreeType**: egy C-könyvtár, ami fontfájlt olvas és glifeket raszterizál. A Chrome és a Firefox is ezt használja (Windowson a DirectWrite-ot). Pontosan azt írjuk meg most kicsiben, amit a FreeType csinál.
@@ Python
A Pillow `ImageFont.truetype("DejaVuSans.ttf", 16)` hívása mögött is a FreeType dolgozik. A `fontTools` csomaggal pedig bele lehet nézni egy fontfájl tábláiba.
@@ Rust
A profi Rust-világban a `ttf-parser` olvassa a fájlt, az `ab_glyph` vagy a `swash` raszterizál. A 16. modulban a kapcsoló mögé a Parley és a Swash kerül.
@@ Érettségi
Gondolj a vektorgrafikára (SVG) a bittérkép (BMP) helyett: az alakzat leírása kicsi és tetszőlegesen nagyítható, a megjelenítéskor kell pixelekké alakítani.
:::

## Mi van egy TTF-fájlban?

A TrueType-fájl (`.ttf`) egy **táblákból álló konténer**, a neve *sfnt* („spline font”). Az elején egy rövid fejléc és egy **táblakönyvtár** (table directory) van: melyik tábla hol kezdődik, és milyen hosszú. Minden táblának négybetűs neve van:

| Tábla | Mi van benne | Mikor kell |
|---|---|---|
| `head` | Általános adatok: hány egység egy em (`unitsPerEm`), a `loca` formátuma | 07-02 |
| `maxp` | Hány glif van a fontban | 07-02 |
| `hhea` | Az alapvonal fölötti és alatti magasság (ascender, descender) | 07-02 |
| `loca` | Hol kezdődik az egyes glifek leírása a `glyf`-ben | 07-03 |
| `glyf` | A glifek körvonalai: pontok és görbék | 07-03 |
| `cmap` | Melyik karakterhez melyik glif tartozik | 07-06 |
| `hmtx` | Mennyivel lép tovább a toll egy glif után | 07-08 |
| `kern` | Mely betűpárok kerüljenek közelebb (pl. „AV”) | 07-08 |

Egy **glif** (glyph) a betű rajza. A karakter és a glif nem ugyanaz: az `á` karakterhez egy glif tartozik, de az a glif két másik glifből (`a` és `´`) van összerakva (07-07). A fontban a glifeknek sorszámuk van (0, 1, 2 …), és a `cmap` köti őket a karakterekhez.

A számok **font-egységben** (font unit) vannak. A DejaVu Sansban 2048 egység egy **em**, vagyis a betűméret. 16px-es szövegnél egy egység 16 / 2048 = 1/128 pixel.

:::note OpenType, WOFF2, .otf
Az **OpenType** a TrueType bővített változata, ugyanazzal a táblás felépítéssel. Egy `.otf` fájlban a körvonalak lehetnek TrueType-görbék (`glyf` tábla, ezt olvassuk) vagy harmadfokú CFF-görbék (`CFF ` tábla, ezt nem). A weben a fontok **WOFF2**-ként utaznak: ez ugyanaz az sfnt, csak tömörítve. A kicsomagolás (Brotli) messzire vinne, ezért mi a nyers `.ttf`-et olvassuk.
:::

## Big-endian: a bájtok sorrendje

Egy 16 bites szám két bájt. A kérdés: melyik jön előbb, a nagyobb helyiértékű vagy a kisebb? A TrueType (és szinte minden hálózati formátum) **big-endian**: előbb a nagyobb helyiértékű bájt. Az `[0x08, 0x00]` bájtpár tehát 0x0800 = 2048, nem 8.

A Windows-gépek processzora (x86) viszont **little-endian**: a memóriában a kisebb helyiértékű bájt van elöl. Ezért nem lehet egyszerűen „ráhúzni” egy `u16`-ot a bájtokra. A Rust minden egész típusnak ad egy átalakító függvényt:

```rust
        Some(u16::from_be_bytes([b[0], b[1]]))
```

A `be` a big-endian rövidítése. Van `from_le_bytes` (little-endian) és `from_ne_bytes` (a gép saját sorrendje) is.

:::compare Bájtsorrend máshol
@@ C#
A `BinaryReader.ReadUInt16()` little-endian. Big-endianhez: `BinaryPrimitives.ReadUInt16BigEndian(span)`.
@@ C++
A klasszikus megoldás az `ntohs` / `ntohl` („network to host short/long”), vagy kézzel: `(b[0] << 8) | b[1]`.
@@ Python
`struct.unpack(">H", data[0:2])`: a `>` jelenti a big-endiant, a `H` az előjel nélküli 16 bitet.
@@ Érettségi
Pont olyan, mint a helyiértékes írás: a 0x0800-ban a `08` a „256-osok” helyén áll. Big-endianben balról jobbra olvasunk, ahogy a számokat is.
:::

## Te jössz: az olvasó

Egy fontfájl olvasása sok-sok számolvasás egymás után: „a 18. bájttól egy `u16`, utána egy `i16` …”. Írjunk erre egy kis segédet!

:::task
Írd meg a `Reader<'a>` struktúrát a `src/reader.rs`-be. Két mezője van: a bájtok (`data: &'a [u8]`) és az aktuális hely (`pos: usize`). A metódusai:

- `new(data)` az elejéről, `at(data, pos)` egy adott helyről indul.
- `pos()` visszaadja a helyet, `skip(n)` átugrik `n` bájtot.
- `u8`, `i8`, `u16`, `i16`, `u32`: kiolvasnak egy számot big-endianben, és továbblépnek utána.
- `tag()`: egy négybetűs név (`[u8; 4]`), pl. `b"glyf"`.
- `f2dot14()`: egy 2.14-es fixpontos szám (07-07-ben kell): egy `i16`, osztva 16384-gyel.

Minden olvasás `Option`-t ad: ha elfogyna az adat, `None`. Így egy sérült fájl nem omlasztja össze a böngészőt.
:::

A tesztek a `reader.rs` végére:

```rust test
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn big_endian_numbers() {
        let data = [0x00, 0x01, 0xFF, 0xFE, 0x12, 0x34, 0x56, 0x78];
        let mut r = Reader::new(&data);
        assert_eq!(r.u16(), Some(1));
        assert_eq!(r.i16(), Some(-2));
        assert_eq!(r.u32(), Some(0x1234_5678));
        assert_eq!(r.u8(), None, "elfogyott az adat");
        assert_eq!(Reader::at(&data, 2).u16(), Some(0xFFFE));
        assert_eq!(Reader::at(&data, 7).u16(), None);
    }

    #[test]
    fn tags_and_fixed_point() {
        let data = *b"glyf\x40\x00\xC0\x00";
        let mut r = Reader::new(&data);
        assert_eq!(&r.tag().unwrap(), b"glyf");
        assert_eq!(r.f2dot14(), Some(1.0));
        assert_eq!(r.f2dot14(), Some(-1.0));
        assert_eq!(r.pos(), 8);
    }

    #[test]
    fn sfnt_header() {
        // a DejaVu Sans első 6 bájtja: a verzió (1.0, vagyis TrueType) és a táblák száma
        let mut r = Reader::new(crate::DEJAVU_SANS);
        assert_eq!(r.u32(), Some(0x0001_0000));
        assert_eq!(r.u16(), Some(20));
    }
}
```

:::hint
Érdemes egyetlen privát segédfüggvényt írni, ami a többit kiszolgálja: „add a következő `n` bájtot, és lépj utánuk”.
```rust
fn take(&mut self, n: usize) -> Option<&'a [u8]>
```
A szelet `get` metódusa nem pánikol, ha a tartomány kilóg, hanem `None`-t ad: `self.data.get(self.pos..self.pos + n)`.
---
A `take`-re építve egy `u16` két sor:
```rust
let b = self.take(2)?;
Some(u16::from_be_bytes([b[0], b[1]]))
```
Az `i16` pedig egy `u16`, aminek a bitjeit előjelesként értelmezzük: `self.u16()? as i16`. A 0xFFFE így -2 lesz (kettes komplemens).
---
A visszaadott szelet élettartama `'a`, nem a `&mut self`-é. Így a kiolvasott bájtok tovább élhetnek, mint maga az olvasó. Ezért kell az `impl<'a> Reader<'a>` és a `-> Option<&'a [u8]>`.
:::

:::solution
```rust
//! Bájtok olvasása big-endian sorrendben: a TrueType-fájlok minden száma így van tárolva.

/// Olvasó egy bájtszeleten. Minden olvasás `Option`: ha elfogyna az adat, `None`.
#[derive(Debug, Clone)]
pub struct Reader<'a> {
    data: &'a [u8],
    pos: usize,
}

impl<'a> Reader<'a> {
    pub fn new(data: &'a [u8]) -> Reader<'a> {
        Reader { data, pos: 0 }
    }

    /// Olvasó, ami a `pos` helyről indul.
    pub fn at(data: &'a [u8], pos: usize) -> Reader<'a> {
        Reader { data, pos }
    }

    pub fn pos(&self) -> usize {
        self.pos
    }

    pub fn skip(&mut self, n: usize) {
        self.pos += n;
    }

    /// A következő `n` bájt, és lépés utánuk.
    fn take(&mut self, n: usize) -> Option<&'a [u8]> {
        let slice = self.data.get(self.pos..self.pos + n)?;
        self.pos += n;
        Some(slice)
    }

    pub fn u8(&mut self) -> Option<u8> {
        Some(self.take(1)?[0])
    }

    pub fn i8(&mut self) -> Option<i8> {
        Some(self.u8()? as i8)
    }

    pub fn u16(&mut self) -> Option<u16> {
        let b = self.take(2)?;
        Some(u16::from_be_bytes([b[0], b[1]]))
    }

    pub fn i16(&mut self) -> Option<i16> {
        Some(self.u16()? as i16)
    }

    pub fn u32(&mut self) -> Option<u32> {
        let b = self.take(4)?;
        Some(u32::from_be_bytes([b[0], b[1], b[2], b[3]]))
    }

    /// Egy négybetűs név, pl. `b"glyf"`.
    pub fn tag(&mut self) -> Option<[u8; 4]> {
        let b = self.take(4)?;
        Some([b[0], b[1], b[2], b[3]])
    }

    /// 2.14-es fixpontos szám: 16384 = 1.0. Az összetett glifek nagyítása ilyen.
    pub fn f2dot14(&mut self) -> Option<f32> {
        Some(self.i16()? as f32 / 16384.0)
    }
}
```
:::

:::why Miért nem `std::io::Read`?
A Rust szabványos könyvtárában van `Read` trait és `Cursor`, amivel bájtfolyamot lehet olvasni. Fájlformátumoknál azonban gyakran **ugrálni** kell: a táblakönyvtár megmondja, hogy a `head` a 611 512. bájtnál van, a `loca` egy harmadik helyre mutat, és így tovább. A teljes fájl úgyis a memóriában van (`include_bytes!`), ezért egy szeletből olvasni egyszerűbb és gyorsabb, mint egy folyamból.

A `Reader` nem másolja a bájtokat, csak hivatkozik rájuk (`&'a [u8]`). Ezt a mintát **zero-copy** olvasásnak hívják, a profi `ttf-parser` is így működik.
:::
