## A dinamikus blokk: a kód is az adatban van

A rögzített kód mindenre ugyanaz, ezért nem igazán jó semmire. Egy magyar szövegben az `á` gyakori, egy HTML-ben a `<`. A legjobb kód minden adatra más. A dinamikus blokk (BTYPE = `10`) ezért **elküldi a saját kódját**, vagyis a kódhosszakat (08-11: a hosszakból minden kiszámolható).

Csakhogy ez 286 + 30 hossz, ami sok lenne. Ezért a hosszakat is tömörítik, egy harmadik Huffman-kóddal. Így a blokk eleje három réteg:

```text Ábra
HLIT  (5 bit) + 257    a literál/hossz-kódok száma (257–286)
HDIST (5 bit) + 1      a távolságkódok száma (1–32)
HCLEN (4 bit) + 4      a kódhossz-kód hosszainak száma (4–19)

HCLEN × 3 bit          ① a kódhossz-kód (code length code) hosszai, furcsa sorrendben
                        ↓  ebből egy Huffman-kód
HLIT + HDIST hossz     ② a literál- és a távolságkód hosszai, ①-gyel kódolva
                        ↓  ebből két Huffman-kód
adat                   ③ a blokk tartalma, mint a 08-11-ben
```

A ② kódhossz-ábécéje 19 szimbólum:

| Szimbólum | Jelentés |
|---|---|
| 0–15 | Ez a hossz |
| 16 | Az előző hossz még 3–6-szor (2 extra bit) |
| 17 | 3–10 darab 0 (3 extra bit) |
| 18 | 11–138 darab 0 (7 extra bit) |

A sok 0 (a nem használt szimbólumok) így pár bitbe fér. Az ① hosszai ebben a sorrendben jönnek: `16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15`. A gyakran használtak vannak elöl, így a végéről a nullák elhagyhatók (ezért kell a HCLEN).

A literál- és a távolsághosszak egyetlen sorozatban jönnek: az első HLIT a literál/hossz-kódé, a maradék HDIST a távolságkódé. Egy 16-os ismétlés át is nyúlhat a kettő határán.

## A gzip: boríték a DEFLATE körül

A szerver nem nyers DEFLATE-et küld, hanem **gzip**-et (RFC 1952). Ez egy fejléc, a DEFLATE-folyam, és egy lezáró:

```text Ábra
1f 8b │ 08 │ jelzők │ idő (4) │ XFL │ OS │ [extra] [név\0] [megjegyzés\0] [CRC16] │ DEFLATE … │ CRC-32 (4) │ hossz (4)
 azon.  mód.                                └──── a jelzők szerint ────┘
```

- `1f 8b`: a „varázsszám” (magic number), ebből ismerni fel egy gzip-fájlt. A `08` a módszer: DEFLATE.
- A **jelzők** (flags) bitjei mondják meg, mi jön még: `0x04` (FEXTRA) 2 bájt hossz és annyi extra bájt, `0x08` (FNAME) a fájl neve egy 0 bájtig, `0x10` (FCOMMENT) egy megjegyzés egy 0 bájtig, `0x02` (FHCRC) 2 bájt fejléc-ellenőrzőösszeg.
- A végén a kicsomagolt adat **CRC-32**-je és **hossza** (kis-endián). A CRC-32 ugyanaz, mint a PNG-íród ellenőrzőösszege (06-07). Ha nem egyezik, az adat megsérült.

Ezért adja vissza az `inflate` azt is, hány bájtot használt el: a lezáró utána kezdődik.

A HTTP-ben a kliens a kérésben jelzi, mit ért: `Accept-Encoding: gzip`. A szerver csak akkor tömörít, ha a kliens ezt kérte, és a válaszban megírja: `Content-Encoding: gzip`. (A mi tesztszerverünk a `/gzip/` címeken mindig tömörít, hogy kipróbálhasd.)

:::compare gzip máshol
@@ C#
`new GZipStream(stream, CompressionMode.Decompress)`, és a `HttpClientHandler.AutomaticDecompression = DecompressionMethods.GZip` beállítással a `HttpClient` magától csinálja, mint mostantól a mi kliensünk.
@@ C++
A zlib `inflateInit2(&strm, 16 + MAX_WBITS)`: a `16 +` jelenti, hogy gzip-fejlécet vár. A `-MAX_WBITS` a nyers DEFLATE.
@@ Python
`gzip.decompress(adat)`. A `zlib.decompressobj(-15)` nyers DEFLATE-et vár, a `zlib.decompressobj(31)` gzip-et. A teszt adatfájlját is a `zlib` modullal készíted.
@@ Érettségi
A tömörítés hatékonysága, a veszteségmentes és a veszteséges tömörítés különbsége gyakori kérdés. A DEFLATE veszteségmentes: a kicsomagolt adat bájtra pontosan az eredeti.

```rust
/// A dinamikus blokk a saját kódját is magával hozza: előbb egy kódhossz-kódot (code length
/// code), és azzal tömörítve a literál- és a távolságkód hosszait.
fn dynamic(bits: &mut BitReader) -> Result<(Huffman, Huffman), InflateError> {
    let hlit = bits.bits(5)? as usize + 257;
    let hdist = bits.bits(5)? as usize + 1;
    let hclen = bits.bits(4)? as usize + 4;
    // a kódhosszak kódjának hosszai ebben a furcsa sorrendben jönnek (a gyakoriak előre)
    const ORDER: [usize; 19] = [
        16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15,
    ];
    let mut cl_lengths = [0u8; 19];
    for &i in &ORDER[..hclen] {
        cl_lengths[i] = bits.bits(3)? as u8;
    }
    let cl = Huffman::new(&cl_lengths);
    let mut lengths: Vec<u8> = Vec::with_capacity(hlit + hdist);
    while lengths.len() < hlit + hdist {
        let symbol = cl.decode(bits)?;
        let (value, repeat) = match symbol {
            0..=15 => (symbol as u8, 1),
            16 => (
                *lengths.last().ok_or(InflateError::BadCode)?,
                3 + bits.bits(2)?,
            ),
            17 => (0, 3 + bits.bits(3)?),
            _ => (0, 11 + bits.bits(7)?),
        };
        for _ in 0..repeat {
            lengths.push(value);
        }
    }
    if lengths.len() > hlit + hdist {
        return Err(InflateError::BadCode);
    }
    Ok((
        Huffman::new(&lengths[..hlit]),
        Huffman::new(&lengths[hlit..]),
    ))
}
```

```rust
pub fn inflate(data: &[u8]) -> Result<(Vec<u8>, usize), InflateError> {
    let mut bits = BitReader::new(data);
    let mut out = Vec::new();
    loop {
        let last = bits.bit()? == 1;
        match bits.bits(2)? {
            0 => stored(&mut bits, &mut out)?,
            1 => {
                let (lit, dist) = fixed();
                codes(&mut bits, &mut out, &lit, &dist)?;
            }
            2 => {
                let (lit, dist) = dynamic(&mut bits)?;
                codes(&mut bits, &mut out, &lit, &dist)?;
            }
            _ => return Err(InflateError::BadBlockType),
        }
        if last {
            return Ok((out, bits.position()));
        }
    }
}
```

```rust
//! gzip (RFC 1952): egy fejléc, a DEFLATE-folyam, és egy lezáró (CRC-32 és a hossz).

use crate::inflate::{InflateError, inflate};

const FHCRC: u8 = 0x02;
const FEXTRA: u8 = 0x04;
const FNAME: u8 = 0x08;
const FCOMMENT: u8 = 0x10;

/// CRC-32 bitenként: ugyanaz az ellenőrzőösszeg, mint a PNG-íróban (06-07).
pub fn crc32(data: &[u8]) -> u32 {
    let mut crc = 0xFFFF_FFFFu32;
    for &byte in data {
        crc ^= u32::from(byte);
        for _ in 0..8 {
            crc = if crc & 1 != 0 {
                (crc >> 1) ^ 0xEDB8_8320
            } else {
                crc >> 1
            };
        }
    }
    !crc
}

/// A nullával lezárt mező (fájlnév, megjegyzés) utáni hely.
fn skip_zero_terminated(data: &[u8], pos: usize) -> Result<usize, InflateError> {
    let len = data
        .get(pos..)
        .and_then(|rest| rest.iter().position(|&b| b == 0))
        .ok_or(InflateError::Truncated)?;
    Ok(pos + len + 1)
}

pub fn gunzip(data: &[u8]) -> Result<Vec<u8>, InflateError> {
    // azonosító (1f 8b), módszer (8 = DEFLATE), jelzők, idő (4), extra jelzők, operációs rendszer
    if data.len() < 18 || data[..3] != [0x1F, 0x8B, 8] {
        return Err(InflateError::BadHeader);
    }
    let flags = data[3];
    let mut pos = 10;
    if flags & FEXTRA != 0 {
        let len = data.get(pos..pos + 2).ok_or(InflateError::Truncated)?;
        pos += 2 + u16::from_le_bytes([len[0], len[1]]) as usize;
    }
    if flags & FNAME != 0 {
        pos = skip_zero_terminated(data, pos)?;
    }
    if flags & FCOMMENT != 0 {
        pos = skip_zero_terminated(data, pos)?;
    }
    if flags & FHCRC != 0 {
        pos += 2;
    }
    let (out, used) = inflate(data.get(pos..).ok_or(InflateError::Truncated)?)?;
    let trailer = data
        .get(pos + used..pos + used + 8)
        .ok_or(InflateError::Truncated)?;
    let crc = u32::from_le_bytes([trailer[0], trailer[1], trailer[2], trailer[3]]);
    let size = u32::from_le_bytes([trailer[4], trailer[5], trailer[6], trailer[7]]);
    if crc != crc32(&out) || size != out.len() as u32 {
        return Err(InflateError::BadChecksum);
    }
    Ok(out)
}
```

:::why Mélyvíz: a Brotli és a Zstandard
A mai böngészők az `Accept-Encoding`-ban többet is kínálnak: `gzip, deflate, br, zstd`. A **Brotli** (`br`, a Google-től) és a **Zstandard** (`zstd`, a Facebooktól) ugyanazt a két ötletet használja (visszahivatkozás és entrópiakódolás), de okosabban. A Brotli például egy beépített, 120 KiB-os szótárral indul, tele gyakori HTML-, CSS- és JS-részletekkel, így már az első bájtoknál van mire visszahivatkozni. Egy weboldal Brotlival átlagosan 15–25%-kal kisebb, mint gzippel. Mi csak `gzip`-et kérünk, így minden szerver olyat küld, amit értünk.

```rust
fn gzip_header_len(data: &[u8]) -> Option<usize> {
    if data.len() < 10 || data[..3] != [0x1F, 0x8B, 8] {
        return None;
    }
    let flags = data[3];
    let mut pos = 10;
    if flags & 0x04 != 0 {
        let len = data.get(pos..pos + 2)?;
        pos += 2 + u16::from_le_bytes([len[0], len[1]]) as usize;
    }
    for flag in [0x08, 0x10] {
        if flags & flag != 0 {
            let mut text = String::new();
            loop {
                let b = *data.get(pos)?;
                pos += 1;
                if b == 0 {
                    break;
                }
                text = format!("{text}{}", b as char);
            }
        }
    }
    if flags & 0x02 != 0 {
        pos += 2;
    }
    (pos <= data.len()).then_some(pos)
}
```

Mi a dinamikus blokk kódhossz-kódjában a 18-as szimbólum, ha utána 7 extra bit `0000101` (= 5) jön?
- [ ] Öt darab 18-as hossz
- [x] 11 + 5 = 16 darab 0 hosszú (nem használt) szimbólum
- [ ] Az előző hossz 18-szor
> A 18 a hosszú nulla-sorozat: 11 és 138 között, a 7 extra bit adja hozzá a 11-hez. A 17 a rövid (3–10), a 16 az előző hossz ismétlése.

:::card
K: Mit küld egy dinamikus DEFLATE-blokk az adat előtt?
V: A saját Huffman-kódjait, kódhosszakként. A hosszakat is tömöríti: egy harmadik, kódhossz-kóddal, ismétlésekkel (16) és nulla-sorozatokkal (17, 18).
:::

:::card
K: Miből áll egy gzip-fájl?
V: Fejléc (`1f 8b 08`, jelzők, idő, és a jelzők szerint név, megjegyzés stb.), a DEFLATE-folyam, és egy lezáró: a kicsomagolt adat CRC-32-je és hossza.
:::
