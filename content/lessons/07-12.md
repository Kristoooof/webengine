## Mi az a CSS-pixel?

A 06-04-ben ígértük, hogy a nagyított kijelzőkre visszatérünk. Itt az ideje. Egy mai laptopon a Windows nagyítása gyakran 125% vagy 150%: a rendszer mindent másfélszer nagyobbra rajzol, hogy a sűrű kijelzőn olvasható maradjon. A Rozsda eddig egy CSS-pixelt egy fizikai pixelnek vett, ezért egy ilyen gépen apró betűkkel írt.

A böngészők két pixelt különböztetnek meg:

- **CSS-pixel** (logikai pixel): amiben a weboldal gondolkodik. Egy `16px`-es betű, egy `600px` széles kártya.
- **Fizikai pixel** (device pixel): a kijelző egy pontja.

A kettő aránya a `devicePixelRatio` (JavaScriptben `window.devicePixelRatio`). 150%-on 1,5: egy 600 CSS-pixeles kártya 900 fizikai pixel széles. A winit ezt `window.scale_factor()` néven adja meg, és kétféle méretet ismer: `LogicalSize` (CSS-pixel) és `PhysicalSize` (fizikai pixel).

```text Ábra
                      CSS-pixel                    fizikai pixel (150%)
ablak:               960 × 720       ── × 1,5 ──►  1440 × 1080
layout:   minden doboz, sor, betűméret   │
          (ugyanaz, mint 100%-on)        │
rajzlista:                               └──► minden téglalap, betűméret × 1,5
egér:                x / 1,5         ◄── ÷ 1,5 ──  az egér helye az ablakban
```

A lényeg: a **layout nem változik**. 150%-on is 960 CSS-pixel széles az oldal, ugyanott törnek a sorok. Csak a rajzolás nagyobb: a rajzlista minden parancsát 1,5-del szorozzuk. A vektoros betűket pedig egyszerűen 24px-en raszterizáljuk 16 helyett, ezért élesek maradnak. (A 8×8-as betűk ilyenkor csúnyák: 1,5-szeres nagyítás nincs, csak 2×. Ezért kellett előbb az igazi betűtípus.)

## 1. A rajzlista nagyítása

:::task

```rust test

    #[test]

                y: 10.0,
                width: 40.0,

            text: String::from("Szia"),
```

:::solution
```rust
fn scale_rect(r: Rect, zoom: f32) -> Rect {
    Rect {
        x: r.x * zoom,
        y: r.y * zoom,
        width: r.width * zoom,
        height: r.height * zoom,
    }
}

fn scale_sides(s: Sides<f32>, zoom: f32) -> Sides<f32> {
    Sides {
        top: s.top * zoom,
        right: s.right * zoom,
        bottom: s.bottom * zoom,
        left: s.left * zoom,
    }
}

impl DisplayItem {
    /// A parancs `zoom`-szorosra nagyítva: CSS-pixelből a kijelző fizikai pixelei.
    pub fn scaled(&self, zoom: f32) -> DisplayItem {
        match self.clone() {
            DisplayItem::Rect {
                rect,
                color,
                radius,
            } => DisplayItem::Rect {
                rect: scale_rect(rect, zoom),
                color,
                radius: radius * zoom,
            },
            DisplayItem::Border {
                rect,
                widths,
                color,
                radius,
            } => DisplayItem::Border {
                rect: scale_rect(rect, zoom),
                widths: scale_sides(widths, zoom),
                color,
                radius: radius * zoom,
            },
            DisplayItem::Text {
                rect,
                baseline,
                text,
                color,
                size,
                bold,
            } => DisplayItem::Text {
                rect: scale_rect(rect, zoom),
                baseline: baseline * zoom,
                text,
                color,
                size: size * zoom,
                bold,
            },
        }
    }
}
```

A `match self.clone()` egy saját másolatot bont szét, így a `text` (`String`) egyszerűen átkerülhet az új parancsba.
:::

:::task
`app.rs`:

1. Az ablak kezdő mérete **logikai**: `LogicalSize::new(WIDTH, HEIGHT)`. 150%-on így 1440 × 1080 fizikai pixeles ablak nyílik, ami ugyanakkorának látszik, mint 100%-on a 960 × 720.

## 5. Rés a dobozok között

Tört nagyításon egy régi kerekítési hiba is előbukkan. A raszterizáló `fill` függvénye a téglalap helyét és **szélességét** külön-külön kerekíti. 125%-on három egymás melletti, 1 CSS-pixeles doboz 0-tól 1,25-ig, 1,25-től 2,5-ig és 2,5-től 3,75-ig tart. A szélességük kerekítve 1, a helyük 0, 1 és 3. A 2. pixel kimarad: **rés** keletkezik.

A helyes megoldás: az **éleket** kerekítjük, és a szélesség a két kerekített él különbsége. Így ahol az egyik doboz véget ér, ott kezdődik a következő, akárhogy kerekítünk.

```rust test
    #[test]
    fn neighbours_meet_without_gaps() {
        // 125%-on három 1 pixeles szomszéd: 0-tól 1,25-ig, 1,25-től 2,5-ig, 2,5-től 3,75-ig
        let mut c = white(6, 1);
        let at = |x: f32, color: Color| DisplayItem::Rect {
            rect: Rect {
                x,
                y: 0.0,
                width: 1.25,
                height: 1.0,
            },
            color,
            radius: 0.0,
        };
        let red = Color::rgb(255, 0, 0);
        let items = vec![at(0.0, Color::BLACK), at(1.25, red), at(2.5, Color::BLACK)];
        rasterize(&mut c, &items, 0, &Typeface::Bitmap);
        // a szélességek kerekítésével a 2. pixel fehér maradna: rés a két doboz között
        assert_eq!(c.pixels, vec![0, 0xFF0000, 0xFF0000, 0, 0xFFFFFF, 0xFFFFFF]);
    }
```

Futtasd előbb a régi `fill`-lel: piros, a 2. pixel fehér (`16777215`). Ez a teszt tehát nem „rossz okból zöld”.

:::solution
```rust
/// A téglalap éleit kerekítjük, nem a szélességét: így két szomszédos téglalap között
/// tört nagyításon (pl. 150%) sem lesz rés vagy átfedés.
fn fill(canvas: &mut Canvas, r: Rect, scroll: i32, color: Color) {
    let (x0, y0) = (r.x.round() as i32, r.y.round() as i32);
    let (x1, y1) = (r.right().round() as i32, r.bottom().round() as i32);
    canvas.fill_rect(x0, y0 - scroll, x1 - x0, y1 - y0, color);
}
```
:::

:::why Mélyvíz: miért nem a kész képet nagyítjuk?
Kézenfekvő lenne 960 × 720-ban rajzolni, és a kész képet 1,5-szeresére nagyítani. A Windows pont ezt csinálja a régi programokkal („DPI-virtualizáció”): ezért elmosódottak a régi programok betűi egy nagy felbontású laptopon. A nagyított kép pixelei között a gép csak **találgat** (interpolál), az eredeti körvonalak már nincsenek meg.

Mi a rajzlistát nagyítjuk, vagyis a **leírást**, még a pixelek előtt: a raszterizáló a valódi körvonalakból dolgozik a végső felbontásban. Ez a vektoros rajzolás egyik legnagyobb előnye, és ezért kell, hogy a rajzlista a layout és a pixelek között legyen (06-01).
