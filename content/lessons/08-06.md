:::goal
Megvan a szerver IP-címe: most **kapcsolódsz** hozzá. Megírod a `tcp::connect`-et, ami a gépnévből címet keres (a `localhost`-ot a hálózat nélkül), kapcsolódik, és időkorlátot állít, hogy egy néma szerver ne fagyassza le a böngészőt. Egy teszt egy saját, a gépeden futó szerverrel beszélget.
:::

## A TCP: egy telefonvonal

Az UDP levelekkel szemben a **TCP** (Transmission Control Protocol) egy telefonhívásra hasonlít: előbb felépül a vonal, utána mindkét fél beszélhet, és amit az egyik mond, azt a másik **sorrendben és hiánytalanul** hallja. Ha egy csomag elveszik, a TCP magától újraküldi. Ha rossz sorrendben érkeznek, sorba rakja őket.

```text Ábra
 a gépem                                      szerver (93.184.215.14:80)
   │ ─── SYN ───────────────────────────────►  │   „beszélhetünk?”
   │ ◄──────────────────────────── SYN-ACK ──  │   „igen, te is?”
   │ ─── ACK ───────────────────────────────►  │   „igen.”
   │                                           │
   │ ═══ bájtfolyam mindkét irányban ═════════ │   (ide jön majd a HTTP)
   │                                           │
   │ ─── FIN ───────────────────────────────►  │   „végeztem.”
```

Ez a **háromutas kézfogás** (three-way handshake). Mindezt az operációs rendszer intézi. Nekünk annyi a dolgunk, hogy a `TcpStream::connect`-et hívjuk, és utána írunk bele (`write_all`) és olvasunk belőle (`read`), mint egy fájlból.

### Folyam, nem üzenetek

A TCP egyetlen fontos tulajdonságát érdemes már most megjegyezni: **bájtfolyam**, nem üzenetek sora. Ha a szerver két darabban küld 100 és 200 bájtot, mi kaphatjuk egyben a 300-at, vagy 150 + 150-ben, vagy bájtonként. A TCP nem jelzi, hol ér véget egy „üzenet”. Ezt az alkalmazás protokolljának kell eldöntenie: a HTTP-ben a sorvégek, a fejlécek végén az üres sor és a `Content-Length` (08-08). Ezért nem szabad azt feltételezni, hogy egy `read` egy egész választ ad.

### Időkorlátok

Két helyen akadhat el a kapcsolat:

- **Kapcsolódáskor**, ha a szerver nem létezik, vagy egy tűzfal elnyeli a csomagokat. A `TcpStream::connect_timeout(cím, idő)` ad erre korlátot (mi 5 másodpercet).
- **Olvasáskor**, ha a szerver elhallgat. A `set_read_timeout` után a `read` hibát ad, ha túl sokáig nem jön semmi (mi 15 másodpercet engedünk).

Időkorlát nélkül egy rossz szerver örökre megfagyaszthatná a böngészőt.

### Melyik címre?

Egy névnek több IP-címe is lehet (a nagy oldalaknak gyakran van). Ha az első nem válaszol, a következővel próbálkozunk. A `localhost`-ot pedig sosem kérdezzük a DNS-től: az RFC 6761 szerint mindig a saját gépet jelenti, a `127.0.0.1`-et.

:::compare TCP máshol
@@ C#
`using var client = new TcpClient(); client.Connect("pelda.hu", 80); var stream = client.GetStream();` A `ReceiveTimeout` tulajdonság az olvasási időkorlát.
@@ C++
`socket(AF_INET, SOCK_STREAM, 0)`, `connect(…)`, `send`, `recv`. A nem blokkoló kapcsolódás időkorláttal C-ben egy egész kis program (`select` vagy `poll`), Rustban egy hívás.
@@ Python
`socket.create_connection(("pelda.hu", 80), timeout=5)`: névfeloldás, a címek végigpróbálása és az időkorlát egyben, pont mint a mi `connect`-ünk.
@@ Érettségi
A TCP megbízható, sorrendhelyes szállítása, és a kapcsolat felépítése és bontása klasszikus hálózati tananyag. A port itt is a „lakásszám”: a 80-as a HTTP-é, a 443-as a HTTPS-é.
:::

        assert_eq!(answer, "SZIA, SZERVER");
        server.join().unwrap();

A második teszt egy saját „szervert” indít egy szálon a `127.0.0.1` egy szabad portján (`TcpListener::bind("127.0.0.1:0")`). Az elfogad egy kapcsolatot, és nagybetűsítve visszaküldi, amit kapott. A harmadik egy olyan portra kapcsolódna, amin senki nem figyel: az operációs rendszer azonnal visszautasítja (`ConnectionRefused`).

:::solution
```rust
//! TCP-kapcsolat egy szerverhez: a név feloldása, aztán `connect`, időkorláttal.

use crate::dns;
use crate::url::Host;
use std::io;
use std::net::{IpAddr, Ipv4Addr, SocketAddr, TcpStream};
use std::time::Duration;

/// A gép IP-címei: a címet magát, a `localhost`-ot a saját gépre, a többit a DNS-től.
pub fn lookup(host: &Host, dns_server: SocketAddr) -> io::Result<Vec<IpAddr>> {
    Ok(match host {
        Host::Ipv4(ip) => vec![IpAddr::V4(*ip)],
        Host::Ipv6(ip) => vec![IpAddr::V6(*ip)],
        // a `localhost` sosem megy ki a hálózatra (RFC 6761)
        Host::Domain(d) if d == "localhost" || d.ends_with(".localhost") => {
            vec![IpAddr::V4(Ipv4Addr::LOCALHOST)]
        }
        Host::Domain(d) => dns::resolve(d, dns_server)?
            .into_iter()
            .map(IpAddr::V4)
            .collect(),
    })
}

/// Kapcsolódás a gép egyik címéhez. Ha az első nem válaszol, jöhet a következő.
pub fn connect(host: &Host, port: u16, dns_server: SocketAddr) -> io::Result<TcpStream> {
    let mut last_error = io::Error::new(io::ErrorKind::NotFound, "a gépnek nincs címe");
    for ip in lookup(host, dns_server)? {
        match TcpStream::connect_timeout(&SocketAddr::new(ip, port), Duration::from_secs(5)) {
            Ok(stream) => {
                // ha a szerver elhallgat, ne várjunk rá örökké
                stream.set_read_timeout(Some(Duration::from_secs(15)))?;
                return Ok(stream);
            }
            Err(e) => last_error = e,
        }
    }
    Err(last_error)
}
```
:::

A tesztben a szerver a `TcpListener::bind("127.0.0.1:0")`-val egy **szabad** portot kér, és a `local_addr()` mondja meg, melyiket kapta. Így a tesztek párhuzamosan is futhatnak, és sosem ütköznek egy foglalt porttal.

:::why Mélyvíz: Happy Eyeballs
A mai gépeknek gyakran IPv4- és IPv6-címük is van, és a nevekhez is jár mindkettő. Ha az IPv6 „félig” működik (a hálózat ismeri, de valahol elakad), a kapcsolódás percekig is lóghat. A böngészők ezért a **Happy Eyeballs** algoritmust használják (RFC 8305): egyszerre indítanak IPv6- és IPv4-kapcsolódást, kis eltolással, és amelyik előbb sikerül, az nyer. A mi `connect`-ünk egyszerűbb: csak IPv4-et kér a DNS-től, és sorban próbálkozik.
:::
